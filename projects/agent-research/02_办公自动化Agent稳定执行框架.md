# 办公自动化 Agent 稳定执行框架：超越提示词分步的方法论

> 本框架旨在回答：为什么"给 Agent 描述 1-2-3-4 步操作"不够稳定，以及如何用 5 层能力模型让 Agent 在网页导数、社媒采集、业务后台等场景中可靠运行。
> 核心观点：稳定性不来自更长的提示词，而来自对任务的精确建模。

---

## 一、为什么"提示词分步"不够用

用自然语言给 Agent 描述操作步骤（如"登录网站 → 进入后台 → 筛选数据 → 导出 Excel"）在 demo 场景下可以工作，但在生产环境中会频繁遇到以下问题：

| 失败模式 | 典型表现 | 根本原因 |
|---------|---------|---------|
| **元素定位失败** | Agent 点击了错误的按钮，或找不到目标元素 | 网页结构变化（class、id 改变）但提示词未更新 |
| **登录态丢失** | 导出时 session 过期，需要重新扫码 | Agent 没有感知登录状态边界 |
| **部分成功无法感知** | 下载了文件但字段不齐全，Agent 继续执行 | 没有验证层，Agent 假设每步都成功 |
| **异常无分支处理** | 遇到验证码、无数据页面，陷入重试循环 | 提示词没有声明"遇到 X 情况时的回退路径" |
| **执行过程不可审计** | 失败了但不知道哪步出错，截图丢失 | 没有状态存储与证据收集机制 |
| **等待不足** | 页面还在加载，Agent 已点击下一页 | 依赖隐式等待，没有显式验证 |
| **下载路径不确定** | 浏览器默认下载目录不确定，文件找不到 | 环境配置未建模 |

**根本原因**：提示词是**声明式指令**，而自动化执行需要**命令式契约**。两者之间的 gap 必须通过显式建模来填补。

## 三、逐层详解

### 第1层：目标建模（Goal Modeling）

**核心问题**：Agent 是否知道什么算"成功"、什么算"失败"、什么情况下应该放弃？

| 建模要素 | 具体内容 | 示例 |
|---------|---------|------|
| **成功条件** | 任务完成的充要条件 | "下载了 .xlsx 文件，包含 2024-Q2 全部销售记录，共 ≥ 1000 行，字段包括 日期/产品/金额/客户" |
| **失败条件** | 明确可检测的失败标志 | "登录失败（验证码无法识别）"、"搜索无结果"、"下载超时（> 60 秒）" |
| **边界条件** | 任务范围的硬边界 | "仅处理中文页面；不处理支付相关操作；不超过 500 条记录/批次" |
| **退出标准** | 什么情况下应该终止 | "重试 3 次仍失败"、"检测到验证码"、"用户未在 10 分钟内响应审批" |
| **输出格式** | 最终交付物的结构 | ".xlsx 文件，字段：xxx，命名规则：YYYYMMDD_报表名.xlsx，保存至：D:\export\" |

**关键设计原则**：每条成功/失败条件必须是**可编程检测的**（布尔表达式），而非模糊的自然语言。

### 第2层：环境建模（Environment Modeling）

**核心问题**：Agent 是否理解运行环境的结构、约束和边界？

| 建模要素 | 具体内容 | 示例 |
|---------|---------|------|
| **网站结构** | 导航路径、关键 URL、可重用 URL 模板 | "后台首页 → 数据中心 → 销售报表（固定路径），URL 模板：/report/sales?start={date}&end={date}" |
| **登录态** | 登录方式、session 时效、失效检测与重登录 | "扫码登录，session 时效 8 小时，失效标志：右上角无用户头像，检测到后执行登出→重新扫码" |
| **下载路径** | 浏览器下载目录、文件名模式、文件大小预期 | "Chrome 默认下载目录：D:\downloads\agent-exports\，文件名前缀：sales_Q{quarter}_，预期大小：100KB~50MB" |
| **文件格式** | 字段定义、数据类型、编码格式 | ".xlsx，日期格式：YYYY-MM-DD，金额：保留2位小数，编码：UTF-8" |
| **权限要求** | 角色权限、数据访问限制、敏感操作标识 | "需要 '报表导出' 权限，Agent 不执行删除/修改操作，所有写操作前需要人类确认" |
| **反爬/限制** | 速率限制、验证码、人机验证触发条件 | "单页停留 < 3 秒，连续操作 > 20 次触发验证码，验证码出现时暂停并通知用户" |

### 第3层：动作建模（Action Modeling）

**核心问题**：Agent 执行每个动作时，是否有明确的执行策略、失败回退和等待条件？

| 建模要素 | 具体内容 | 示例 |
|---------|---------|------|
| **点击序列** | 操作序列（含元素定位策略） | "使用文字定位：找含'导出'文本的按钮（文字匹配优先于 XPath）；备选：aria-label='导出报表'" |
| **筛选逻辑** | 时间范围、字段筛选、多条件组合 | "日期范围：2024-04-01 至 2024-06-30；省份：广东；产品类别：全部；代理商：全部" |
| **重试策略** | 重试次数、退避策略、可恢复错误 vs 不可恢复错误 | "网络超时：等待 5s 后重试，最多 3 次；元素未找到：增加等待 2s，最多 2 次；验证码：标记失败并暂停" |
| **异常切换** | 不同异常类型的分支处理 | "遇到弹窗 → 关闭弹窗 → 继续；遇到无数据页面 → 记录 → 跳过该批次；遇到权限不足 → 记录 → 通知用户" |
| **等待条件** | 显式等待（不等同于固定 sleep） | "等待条件：等待 URL 包含 '/report' 或页面包含 '销售报表' 标题，超时 30s 后标记失败" |
| **操作原子性** | 哪些操作是不可分割的 | "登录 → 验证登录态 → 进入后台，三步合一视为一个原子操作；任一步失败则整个原子操作回退" |

### 第4层：验证建模（Verification Modeling）

**核心问题**：Agent 是否在每步操作后验证了结果，而不仅仅假设操作成功？

| 验证类型 | 检测方法 | 失败时的处理 |
|---------|---------|-----------|
| **步骤后验** | 操作后立即检查页面变化或 API 响应 | 记录错误并重试，或进入异常分支 |
| **字段校验** | 检查导出字段是否完整、格式是否正确 | 重新执行导出，或降级采集（减少字段） |
| **数据完整性** | 记录数是否符合预期、时间范围是否正确 | 触发人工审核 |
| **截图存证** | 关键步骤截图存档（防止事后争议） | 作为审计日志输出 |
| **变更检测** | 操作前后对比关键 UI 元素状态 | 检测异常变化（如页面被意外刷新） |

**验证优先原则**：每步动作后必须紧跟一个验证步骤，验证通过后才进入下一步。这是"稳定"二字的本质。

### 第5层：审计与记忆（Memory & Reporting）

**核心问题**：Agent 执行过程是否可回溯、可复盘、可审计？

| 要素 | 内容 |
|------|------|
| **执行日志** | 每步操作的时间戳、操作类型、输入、输出、结果（成功/失败/跳过） |
| **截图序列** | 关键步骤的截图，命名包含时间戳和操作描述 |
| **失败分类** | 将失败归类（网络/元素/登录/权限/验证码/未知），便于诊断 |
| **步骤回放** | 可按时间线回放整个执行过程 |
| **证据包** | 将日志 + 截图 + 最终输出打包为可交付的审计报告 |
| **人类审批点** | 在高风险操作（导出、删除、提交）前暂停，等待人工确认 |

## 四、精辟提示词 vs 冗长提示词

> "精辟的提示词"不是更详细的提示词，而是更精确的**契约**。

### 4.1 自然语言流水账（不稳定）

```
"请登录后台系统，进入'数据中心' -> 点击'销售报表' ->
 选择日期范围为2024-Q2 -> 点击'导出Excel' ->
 等待下载完成后检查文件是否正确"
```

问题：Agent 不知道什么是"正确"，不知道下载失败怎么办，不知道等待多久，不知道遇到验证码怎么办。

### 4.2 状态机契约（稳定）

```
# 任务：导出2024-Q2销售报表

## 成功定义
- 获得 .xlsx 文件
- 包含字段：日期, 产品, 省份, 代理商, 金额
- 记录数 >= 预期最小值（可配置，默认100）
- 时间范围：2024-04-01 至 2024-06-30

## 状态机
STATE: INIT → LOGIN → NAVIGATE → FILTER → EXPORT → VERIFY → DONE
STATE: INIT → LOGIN → NAVIGATE → FILTER → VERIFY_FAIL → (RETRY or ABORT)
STATE: INIT → LOGIN → CAPTCHA → (NOTIFY_USER or ABORT)

## 允许失败的分支
- CAPCHA: 通知用户协助，完成后继续
- NETWORK_TIMEOUT: 重试3次，间隔5s，仍失败则 ABORT
- NO_DATA: 记录空结果，继续下一批次，不 abort
- PERMISSION_DENIED: 立即 ABORT，通知用户

## 验证规则
每步操作后必须验证：
- LOGIN: 检查右上角用户头像是否存在
- NAVIGATE: 检查URL包含 '/report/sales'
- FILTER: 检查页面显示的日期范围文本
- EXPORT: 检查文件大小 > 0 且 < 50MB

## 证据要求
- LOGIN 完成后截图存档（login_success_{timestamp}.png）
- EXPORT 完成后截图存档（export_done_{timestamp}.png）
- 最终输出文件重命名为：sales_2024Q2_{timestamp}.xlsx
```

## 五、与浏览器 Agent 架构的对应关系

当前行业主流的浏览器 Agent 架构（如 Browser Use、Skyvern、Qoder Browser Agent）本质上是上述 5 层模型的工程实现：

| 本框架层 | Browser Agent 组件 | 关键技术 |
|--------|------------------|---------|
| 目标建模 | Spec / Goal Definition | 自然语言规格 → 可验证条件 |
| 环境建模 | Browser Config / Session Management | Playwright/CDP 连接、cookie 管理 |
| 动作建模 | Action Planner / DOM Selector | 文字定位、语义选择器、ARIA 标签 |
| 验证建模 | Result Validator / Screenshot | 页面状态对比、结构化提取、截图对比 |
| 审计建模 | Memory Store / Audit Log | 执行日志、截图序列、JSON 结构化记录 |

**核心差距**：大多数开源框架只实现了动作层和部分验证层，缺乏目标建模与环境建模的显式声明，导致 Agent 在边界情况下行为不可预测。

## 六、实施建议

### 6.1 实施顺序

1. **先建模，后执行**：先写清楚成功/失败定义，再让 Agent 执行
2. **先简单场景**：从"登录 → 读数据 → 导出"这类单路径场景开始
3. **先验证，后扩展**：每加一个分支场景，先写出验证规则，再写动作
4. **先日志，后优化**：先用 JSON 结构化日志，验证稳定后再优化日志格式

### 6.2 关键反模式

| 反模式 | 表现 | 正确做法 |
|--------|------|---------|
| 把所有规则塞进系统提示词 | 提示词越来越长，Agent 开始遗忘关键约束 | 外部配置文件 + 动态注入 |
| 用固定 sleep 等待 | 在不同网络环境下表现不一致 | 用条件等待（等待特定元素出现） |
| 不记录失败原因 | 每次失败都重新诊断 | 结构化失败分类 + 错误码 |
| 跳过验证步骤 | "应该成功了，继续" | 强制每步验证，验证失败立即分支 |
| 单一提示词适配所有网站 | 登录态、结构、反爬各不相同 | 按网站/系统单独建模 |

### 6.3 与 Qoder Quest 的 Spec-Driven 对比

Quest 的 Spec-Driven 开发流程与本框架的"目标建模"高度一致——两者都强调**在执行前先明确验收标准**。区别在于：

- Quest 的 Spec 面向**代码开发**，接受标准是代码行为
- 本框架的 Spec 面向**网页/办公自动化**，接受标准是数据完整性和执行稳定性

---

*本框架强调：稳定性是设计出来的，不是调试出来的。5 层模型不是相互独立的模块，而是每层都为下一层提供可靠的输入，最终让 Agent 的输出可预测、可验证、可审计。*
