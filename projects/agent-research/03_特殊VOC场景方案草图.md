# 特殊 VOC 场景方案：七鱼评价分类与未知场景发现

> 本框架针对"七鱼用户评价"等客服场景中的非结构化文本处理，提供从原始数据到洞察报告的完整方法论。适用于需要超越规则引擎的语义分类、未知类目发现、场景预测等需求。

---

## 一、业务背景与问题定义

### 1.1 七鱼评价场景的特点

| 特点 | 说明 | 对方案的影响 |
|------|------|-----------|
| **多来源** | 网页导出/Excel/API，数据格式可能不一致 | 需统一预处理管道 |
| **短文本为主** | 用户评价通常在 50~500 字，短文本分类挑战大 | 嵌入模型 + 小样本分类 |
| **标签不完整** | 现有标签体系可能覆盖 70%，大量文本无标签 | 开放集分类 + 未知发现 |
| **时效性强** | 用户投诉有热点效应，需实时监测 | 定期批处理 + 异常波动告警 |
| **情绪混杂** | 同一条评价可能同时包含正负面情绪 | 多标签分类 + 情感强度 |
| **专业术语** | 行业特定词汇（物流、品质、功能） | 领域适配 / 提示词工程 |
| **多语言（可选）** | 部分跨境平台含英文评价 | 多语言模型或翻译管道 |

### 1.2 规则引擎 vs 语义分类的决策边界

**何时用规则引擎（关键词/正则）：**

| 条件 | 判断 |
|------|------|
| 标签集合稳定且封闭 | 未来 1 年内不太可能新增标签 |
| 标签定义精确无歧义 | "质量问题"与"服务态度"边界清晰 |
| 数据量小但高价值 | < 1000 条/天，允许人工逐条审核 |
| 需要 100% 可解释性 | 质检/法务场景，决策必须可解释 |
| 标签与业务强绑定 | "物流延迟 ≥ 3 天"这类量化条件 |

**何时升级到语义分类（LLM）：**

| 条件 | 判断 |
|------|------|
| 标签边界模糊 | "功能问题"和"体验问题"存在交叉 |
| 同义词众多 | "卡顿/闪退/打不开/进不去"都指同一问题 |
| 需要捕捉新场景 | 投诉中出现未在标签体系中的新问题 |
| 数据量大 | > 1000 条/天，人工无法全覆盖 |
| 需要情感强度 | "不满意"与"极度不满"之间的连续量 |
| 需要上下文理解 | 同一词在不同业务语境下含义不同 |

**决策原则**：先用规则引擎覆盖高置信度场景（召回率可能只有 50%），剩余模糊数据走语义分类，两层结果合并输出。

## 三、分层详解

### 第1层：规则引擎层（高置信度分类）

**目的**：用关键词/正则精确覆盖明确类目，留下模糊数据给语义层。

**实现要点**：

```python
# 示例：关键词分类规则
RULES = {
    "物流延迟": {
        "keywords": ["延迟", "晚到", "超时", "等了.*天", "物流.*慢"],
        "exclude": ["提前发货", "物流很快"],
        "confidence": 0.95  # 高置信度，直接输出
    },
    "质量问题": {
        "keywords": ["坏了", "破损", "有划痕", "不能用了", "质量问题"],
        "min_length": 10,  # 避免短文本误判
        "confidence": 0.90
    }
}
```

**输出**：标签 + 置信度 + 原始文本引用

### 第2层：语义分类层（主体分类）

**目的**：用 LLM 对规则层无法处理的数据进行语义分类。

**技术选型**：

| 方案 | 适用规模 | 成本 | 延迟 | 推荐度 |
|------|---------|------|------|--------|
| **小样本分类（Few-shot）** | < 5 万条/批 | 中 | 低 | ★★★★★ |
| **微调专用分类模型** | > 10 万条/天 | 高（训练成本） | 中 | ★★★★ |
| **Embedding + 语义搜索** | 中等 | 低 | 中 | ★★★ |
| **多标签分类（LLM API）** | 小量 | 高 | 高 | ★★ |

**推荐：小样本分类（Few-shot Classification）**

核心思路：每类提供 3~5 个典型示例 + 2 个边界示例，LLM 根据示例推断分类：

```
示例（Few-shot Prompts）：

你是一个客服评价分类专家。根据以下示例，将每条评价分类到对应标签。

【配送延迟类】
示例1："等了5天才到，都超过承诺时间了" → 配送延迟
示例2："发货很快，第二天就到了" → （不属于此类）

【产品功能类】
示例1："App经常闪退，根本没法用" → 产品功能
示例2："功能挺全的，就是有点复杂" → （不属于此类）

【客服服务类】
示例1："客服态度很差，爱答不理的" → 客服服务
示例2："客服很专业，解决了我的问题" → （不属于此类）

【未知问题】如果评价不属于以上任何类，请输出"未知类"并给出你的理由。

待分类评价：{text}
```

**关键技巧**：
- 边界示例（易混淆的案例）比正面示例更重要
- 每类提供至少 1 个"同类但不属于此类"的反例
- 置信度低于阈值（如 0.7）的结果发往聚类发现层

### 第3层：聚类发现层（未知类目发现）

**目的**：自动发现现有标签体系未能覆盖的新投诉场景。

**技术方案：聚类 → LLM 标签生成（GLEAN 框架启发）**

```
Step 1: Embedding 聚类
- 用中文语义嵌入模型（text-embedding-3-small 或 BGE）
- 用 HDBSCAN 聚类（自动确定 K，无需预设）
- 过滤：丢弃 < 10 条的小簇（可能是噪声）

Step 2: 簇标签生成
- 对每个簇，随机抽取 5 条样本 → LLM 生成标签 + 描述
- 标签命名规范：[场景]-[触点]-[问题性质]

Step 3: 评估与归类
- 新簇 vs 已知标签：计算语义相似度
  - 相似度 > 0.85：归入已知标签（可能是现有标签的子集）
  - 相似度 0.6~0.85：标记为"疑似新场景"，进入人工审核队列
  - 相似度 < 0.6：标记为"新类目建议"

Step 4: 标签体系演化
- 每周汇总"新类目建议" → 业务方评审
- 确认后加入标签体系 → 下周期自动覆盖
```

**防止标签爆炸的策略**：
- 初始允许的最大新标签数：5 个/周期
- 新标签需满足：出现频次 > 总样本的 0.5% + 人工确认
- 每个新标签需附带"同义词列表"（减少表达变异）

### 第4层：场景抽取层（Scene Extraction）

**目的**：从投诉文本中抽取结构化信息，而非仅分类。

| 抽取字段 | 示例 | 方法 |
|---------|------|------|
| **场景** | "退款流程"、"物流查询"、"产品使用" | NER + LLM 抽取 |
| **触点** | "APP"、"客服热线"、"快递员" | NER + 触点知识库匹配 |
| **责任方** | "商家"、"平台"、"物流公司"、"用户自身" | 归因分类（Few-shot） |
| **影响程度** | "轻微不便"、"财产损失"、"安全隐患" | 多维评分 + LLM 判定 |
| **期望处理** | "退款"、"补发"、"道歉"、"赔偿" | 意图识别（Few-shot） |

**输出结构**：

```json
{
  "original_text": "等了7天还没到，都超过承诺时间3天了，东西根本用不上",
  "labels": ["配送延迟"],
  "label_confidence": 0.95,
  "scene_extraction": {
    "scenario": "物流配送",
    "touchpoint": "快递",
    "responsibility": "物流公司",
    "impact_level": "中等影响",
    "delay_days": 7,
    "promised_days": 4,
    "user_expectation": "退款/赔偿"
  },
  "sentiment": {
    "overall": "negative",
    "intensity": 0.82,
    "dimensions": {"物流": -0.95, "时效": -0.90}
  },
  "is_new_category": false,
  "evidence_snippet": "等了7天还没到，都超过承诺时间3天了"
}
```

### 第5层：情感分析层（Sentiment Analysis）

**超越二分类**：不仅判断"正面/负面"，还分析：

| 分析维度 | 输出 |
|---------|------|
| **整体情感** | positive / neutral / negative |
| **情感强度** | 0.0 ~ 1.0（连续量） |
| **多维情感** | {"物流": -0.95, "价格": 0.1, "功能": 0.3} |
| **情感转折** | 前正后负 / 前负后正 / 单向 |
| **极端词检测** | "极差"、"完全不能用"、"史上最烂" → 触发升级告警 |

### 第6层：报表与告警层

#### 6.1 VOC 日报 / 周报

| 指标 | 说明 |
|------|------|
| 各标签分布及环比变化 | 发现热点转移 |
| 新发现类目 | 聚类层输出 |
| 平均情感强度趋势 | 整体满意度走向 |
| Top-N 高频问题 | 优先处理列表 |
| 异常波动检测 | 某类投诉突增 > 20% 触发告警 |
| 用户原话引用 | 每个问题配 2~3 条真实评价（保留原文语气） |

#### 6.2 热点聚类可视化

```
周维度  配送延迟  质量问题  客服服务  产品功能  新发现类
─────────────────────────────────────────────────
W1        23%       18%      12%       8%       3%
W2        31%↑      17%      13%       7%       4%↑
W3        28%↓      19%↑     11%↓      6%       2%
W4        19%↓      21%↑     10%↓      9%↑     1%
```

#### 6.3 异常波动告警规则

| 告警级别 | 触发条件 | 通知方式 |
|---------|---------|---------|
| 🔴 P0 紧急 | 某类投诉环比 > +50%，或情感强度骤降 > 0.3 | 即时推送 + 人工介入 |
| 🟡 P1 关注 | 某类投诉环比 > +20%，或新类目出现频率 > 5% | 日报摘要 |
| 🔵 P2 观察 | 情感强度连续 3 天下降 | 周报记录 |

## 四、双读者输出设计

本框架要求最终输出同时服务两类读者：

### 4.1 面向"圈内研究者"

| 内容 | 目的 |
|------|------|
| 模型边界说明 | 每个分类模型的准确率 / 召回率 / F1 |
| 误差分析 | 哪些类型的文本容易误分类，错误是否系统偏斜 |
| 架构决策记录 | 为什么选择 Few-shot 而非微调，trade-off 分析 |
| 标签演化日志 | 每周期标签体系的变化记录（便于追溯） |
| 冷启动数据 | 第一批标签如何建立（人工标注 vs LLM 辅助） |

### 4.2 面向"圈外业务方"

| 内容 | 目的 |
|------|------|
| 结论摘要（3 条） | 本周期最重要发现，1 分钟看完 |
| 可操作建议 | "本周物流延迟投诉上升 31%，建议优先优化 X" |
| 趋势图表 | 折线图（情感趋势）、柱状图（标签分布）、热力图（新类发现） |
| 用户原话 | 每个问题配真实评价，保留原始语气，增强说服力 |
| 竞品对比（如可获取） | 与行业平均对比，当前表现位置 |

## 五、实施路线图

### Phase 1：快速上线（1~2 周）

- [ ] 接入数据源（API / Excel），建立预处理管道
- [ ] 部署规则引擎层（覆盖高频明确标签）
- [ ] 建立 Few-shot 语义分类（小样本分类，无需训练）
- [ ] 基础 VOC 日报（标签分布 + 情感趋势）

### Phase 2：能力增强（3~4 周）

- [ ] 部署聚类发现层（未知类目自动发现）
- [ ] 场景抽取层（NER + 触点识别）
- [ ] 异常波动告警（P0/P1 级别）
- [ ] 双读者输出格式落地

### Phase 3：持续优化（持续迭代）

- [ ] 标签体系演化机制（每周评审 + 更新）
- [ ] 模型评估仪表板（分类准确率持续监控）
- [ ] 业务价值量化（投诉率下降 / 满意度提升关联分析）

## 六、技术依赖清单

| 组件 | 推荐技术 | 备选 |
|------|---------|------|
| 文本嵌入 | text-embedding-3-small / BGE-large-zh | 本地 Embedding API |
| 聚类算法 | HDBSCAN（自动确定 K） | sklearn KMeans |
| LLM 分类 | GPT-4o-mini / Claude Haiku（低成本） | 本地 LLM |
| 情感分析 | LLM API（多维输出） | 中文情感词典 + 规则 |
| 调度系统 | Cron / Airflow | 无服务器（每日触发 Lambda） |
| 数据存储 | PostgreSQL（结构化）+ Qdrant（向量） | MySQL + 纯文件 |
| 可视化 | Streamlit / Metabase | Excel 模板 |
