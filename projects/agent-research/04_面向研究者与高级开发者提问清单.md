# 面向研究者与高级开发者的 Agent 架构提问清单

> 本清单用于访谈、需求沟通或产品评审。每组问题后附"为什么这题重要"及"可追问的二级问题"。适合发给：Agent 框架研究者、AI 产品经理、Agent 开发团队负责人。

---

## 组 A：架构与系统设计

### A1. 单 Agent 与多 Agent 的分工边界

**核心问题**：在什么任务规模或复杂度下，你会选择从单 Agent 切换到多 Agent 协作？切换的决策信号是什么？

> **为什么这题重要**：多 Agent 不是免费的午餐——上下文传递有损耗，任务分解有成本。如果在没有必要时引入多 Agent，会增加系统的不可预测性。知道切换边界是架构决策的关键。

- **二级追问**：如果单 Agent 在某个任务上准确率是 85%，多 Agent 能提升到多少？成本增加多少？什么情况下多 Agent 反而会降低质量？

---

### A2. 记忆与上下文管理

**核心问题**：Agent 在长对话或长任务中，如何管理"什么该记住、什么该遗忘"？是否有人工可配置的遗忘策略？

> **为什么这题重要**：上下文窗口是有限的，但业务场景要求 Agent 能跨天、跨周记住关键信息。上下文管理的质量直接影响 Agent 的实用性和成本。

- **二级追问**：在任务中断后恢复时，如何确保"已压缩的记忆"中包含了足够的上下文？记忆存储的持久化粒度是什么（每轮对话？每步操作？关键决策点？）？

---

### A3. 架构的可升级性

**核心问题**：你们的 Agent 架构是否支持模型热替换（即在不改变上层架构的情况下，用新模型替换旧模型）？架构中哪些部分是与模型强耦合的？

> **为什么这题重要**：模型能力在快速演进，2026 年最优的模型到 2027 年可能不是最优。如果架构与模型强耦合，升级模型意味着重写系统。

- **二级追问**：你们如何处理模型能力边界的变化对系统行为的影响？当模型开始出现"幻觉"或"退化"时，系统是否有降级策略？

---

## 组 B：任务执行与稳定性

### B1. 网页操作的稳定性保障

**核心问题**：当目标网站的 HTML 结构发生变化（class 名称改变、元素移位）时，Agent 如何保持鲁棒？是否有自动适配机制，还是依赖人工维护选择器？

> **为什么这题重要**：这是办公自动化场景中最常见的失败原因。网站改版是常态，而人工维护选择器的成本极高。

- **二级追问**：你们是否测试过系统在"网站小幅改版"场景下的成功率？如果成功率下降，是否有监控和告警机制？是否使用语义选择器（如"点击含'提交'文字的按钮"）替代硬编码 XPath？

---

### B2. 登录态管理与异常恢复

**核心问题**：当 Agent 在执行过程中遇到 session 过期或登录态丢失时，如何检测、如何恢复？是否有"幂等"的执行策略（从任意中间状态重新开始）？

> **为什么这题重要**：长任务（数小时的网页操作）中，登录态过期几乎是必然事件。如果恢复策略不完善，整个任务可能需要从头开始。

- **二级追问**：Agent 如何判断"登录已失效"而不是"操作失败"？是否有状态机来记录执行进度，实现断点续传？

---

### B3. 人类审批点的设计

**核心问题**：你们如何决定"哪些步骤需要人类审批"？是否有基于风险级别的自动审批策略（如低风险操作自动通过，高风险操作触发审批）？

> **为什么这题重要**：太多审批点会降低自动化效率；太少审批点会引入风险。这是一个业务价值与风险控制的权衡问题。

- **二级追问**：对于"导出数据到本地"这类操作，你们是视为低风险（自动执行）还是高风险（需要审批）？审批流程的 SLA 是多久？超时未审批时，系统是等待还是自动取消？

---

## 组 C：特化能力与业务适配

### C1. Agent 学习特定业务软件的机制

**核心问题**：当需要让 Agent 操作一个全新的业务系统（如某品牌的 ERP、CRM 或内部后台）时，你们的训练/适配流程是什么？需要多少样本或文档？

> **为什么这题重要**：每个业务系统都有其独特性——不同的登录流程、不同的数据结构、不同的错误处理。能否低成本地将 Agent 适配到新系统，是产品化的关键。

- **二级追问**：是否支持"从操作演示中学习"（如观看人类操作一次后，Agent 能复现该操作）？学习的结果是持久化的还是每次任务都需要重新学习？

---

### C2. 知识与技能的差异化

**核心问题**：你们如何区分"知识"（事实性信息，如"这个按钮在哪"）和"技能"（过程性能力，如"如何登录这个系统"）？两者在 Agent 架构中的存储和复用方式是否不同？

> **为什么这题重要**：如果两者不区分，Agent 会把"知识"当作"技能"来执行，导致知道"应该做什么"但不知道"如何做"。

- **二级追问**：当业务系统升级导致"技能"失效但"知识"仍然有效时，如何处理？是否有技能版本管理和回滚机制？

---

## 组 D：VOC 与分类问题

### D1. 未知类目的发现策略

**核心问题**：在VOC分类场景中，如何发现现有标签体系未能覆盖的新投诉类型？发现后，是自动加入标签体系还是需要人工审核？审核流程的响应时效是多少？

> **为什么这题重要**：业务在变化，投诉类型也在演化。如果标签体系是封闭的，系统会逐渐失去覆盖新场景的能力。但如果开放得过快，又会导致标签爆炸。

- **二级追问**：你们如何区分"真正的未知类目"和"边界模糊导致的误分"？未知类目的置信度阈值如何设定？谁有权限批准新标签加入体系？

---

### D2. 标签体系的演化机制

**核心问题**：随着业务发展，标签体系如何演化？是否支持"标签合并"（两个相似标签合并为一）、"标签分裂"（一个宽泛标签拆分为多个细粒度标签）？

> **为什么这题重要**：VOC 分类系统的长期价值取决于标签体系能否随业务演进。一次性设计标签体系而后冻结，会导致系统逐渐失效。

- **二级追问**：当标签发生变化时，历史数据如何重新标注？是否需要全量重跑分类模型？重跑的频率如何控制？

---

### D3. 证据可解释性

**核心问题**：当业务方质疑某个分类结果时（如"这条评价明明是物流问题，为什么分到了产品功能？"），Agent 能否提供决策依据（如"因为文本中包含关键词 X"）？

> **为什么这题重要**：VOC 分类结果直接影响业务决策（如资源分配、优先级排序）。缺乏可解释性的分类结果，在业务侧难以建立信任。

- **二级追问**：分类结果是否附带"置信度"和"证据片段引用"？置信度低于某个阈值的结果，是否有特殊的处理流程（如强制人工复核）？

---

### D4. 情感分析的粒度

**核心问题**：你们对情感分析的要求是"正面/负面"二分类，还是需要"情感强度"（0~1 的连续量）和"多维情感"（如"对物流负面但对功能正面"）？为什么？

> **为什么这题重要**：情感分析的粒度直接影响系统复杂度和成本。二分类最容易实现，但业务价值有限；多维情感分析价值更高，但需要更复杂的模型和标注策略。

- **二级追问**：当同一条评价中包含多种情感时（如"物流很快但产品很差"），如何处理？是否支持多标签情感输出？

---

## 组 E：交互与用户体验

### E1. 提示词与规格书的设计

**核心问题**：你们如何设计 Agent 的提示词/规格书（Spec）？是否有模板化的 Spec 生成流程？当 Spec 与实际执行产生偏差时，如何发现和处理？

> **为什么这题重要**：Spec 是 Agent 行为的契约。Spec 的质量直接决定执行质量。而 Spec 与执行之间的偏差，是系统不可预测性的主要来源。

- **二级追问**：你们是否有 Spec 的版本管理？当 Spec 更新后，如何确保 Agent 使用的是最新版本？是否有"Spec drift"（规格漂移）检测机制？

---

### E2. 状态机的表达能力

**核心问题**：Agent 执行过程中的状态机（State Machine）表达能力有多强？是否支持嵌套状态、分支合并、超时处理、并发分支？

> **为什么这题重要**：简单的顺序执行无法覆盖实际场景中的分支、等待、异常处理。状态机的表达能力决定了系统能处理多复杂的业务流程。

- **二级追问**：当状态机遇到"未建模的状态"时（如下一环节的页面不是预期中的任何一种），Agent 的默认行为是什么？是暂停等待指令，还是尝试推断下一步？

---

### E3. 回放与审计界面

**核心问题**：业务方能否回放 Agent 的执行过程？回放界面是否支持"从第 N 步重新执行"（而不是从头开始）？

> **为什么这题重要**：当执行失败时，业务方需要能够诊断"哪一步开始出错"。缺乏回放能力的系统，会让调试成本大幅上升。

- **二级追问**：执行日志和截图的保存策略是什么？保存多久？是否有日志的访问权限控制（不同角色看到不同的日志详细程度）？

---

## 组 F：评估与业务价值

### F1. 成功率的定义与度量

**核心问题**：你们如何定义 Agent 的"成功率"？是"任务完全成功"还是"任务部分成功"？部分成功的边界是什么？

> **为什么这题重要**：成功率是 Agent 系统最核心的评估指标，但"成功"的定义往往比想象中复杂。定义不清的成功率会导致错误的优化方向。

- **二级追问**：
  - 如果任务"90% 完成了，最后一步失败了"，算成功还是失败？
  - 如果任务"完成了但输出了错误的数据"，算成功还是失败？
  - 成功率是否按任务类型分别统计（如"网页登录类" vs "数据导出类"）？

---

### F2. 稳定性 vs 速度的权衡

**核心问题**：在设计 Agent 系统时，你们默认优先"稳定性"（多验证、多等待）还是"速度"（快速执行、减少中间确认）？这个权衡在什么场景下会切换？

> **为什么这题重要**：稳定性与速度是一对基本矛盾。过度追求稳定性会让 Agent 变得迟钝；过度追求速度会增加失败率。在不同业务场景下，最优权衡点不同。

- **二级追问**：在"夜间批量执行"场景下，你们是否允许 Agent 采用更激进的速度策略（因为失败后可以重新调度）？在"实时用户交互"场景下，是否采用更保守的策略？

---

### F3. 业务价值的量化

**核心问题**：如何量化 Agent 系统的业务价值？是用"节省的人工小时数"，还是"错误率的下降"，还是"NPS/CSAT 的变化"？哪种度量方式最能反映 Agent 的真实价值？

> **为什么这题重要**：Agent 系统的投入产出比难以量化是推广的主要障碍。清晰的价值度量框架，是获得业务方支持的关键。

- **二级追问**：你们是否追踪 Agent 执行失败后的"人工介入成本"（即 Agent 失败后需要人工介入处理的工时）？这个指标如何与 Agent 的成功率关联？

---

## 使用建议

### 如何使用本清单

1. **访谈模式**：将每组问题作为半结构化访谈的提纲，每题留 10~15 分钟讨论时间
2. **书面评审**：将清单发给受访者书面作答，适合异步收集
3. **产品评审**：按组逐一过，每个问题评估"Yes / Partial / No / N/A"
4. **差距分析**：将所有问题按维度（A~F）汇总评分，识别架构最薄弱的地方

### 问题优先级建议

| 优先级 | 问题 | 原因 |
|--------|------|------|
| P0（必须问） | A1、A3、B1、F1 | 这些决定了架构的核心能力和基本可行性 |
| P1（强烈建议问） | B2、B3、D1、D3、E2 | 这些影响系统的实用性和可维护性 |
| P2（视时间而定） | A2、C1、C2、D2、D4、E1、E3、F2、F3 | 这些影响系统的长期演进和业务价值 |

---

*本清单的 6 组问题覆盖了 Agent 系统从架构设计到业务价值的完整链条。每组问题都可独立使用，也可组合成完整评审流程。问题设计尽量避免了"是否支持 X 功能"的简单询问，而聚焦于"如何设计 X"和"如何评估 X"，以获取更深层的架构决策信息。*
